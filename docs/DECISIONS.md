# Архитектурные решения

Зачем сделано именно так. Код отвечает на вопрос «как», этот файл — на «почему»,
чтобы решения не переоткрывались заново и не отменялись по недоразумению.

## Транспорт: только SSH, не RouterOS API

`/export terse hide-sensitive` — канонический полный конфиг одним текстом: его можно
дифать, грепать и он разбит по путям меню. Через API пришлось бы обходить ~80 меню
по отдельности и собирать нечто похожее вручную.

Дополнительный аргумент из практики: на части устройств API-порт 8728 закрыт, а SSH
открыт почти всегда. Один транспорт — один пользователь, один набор прав, один модуль.

## Хранилище: git, не таблица в БД

`/data/configs/<slug>/export.rsc`, один коммит на прогон сбора. Бесплатно даёт историю,
диффы и ответ на «когда появилось это правило». SQLite остаётся для того, что конфигом
не является: пользователи UI, чаты, учёт расходов, аудит.

Ключевая деталь: из экспорта срезается шапка (`# <дата> by RouterOS ...`). Без этого
таймстамп менялся бы каждый сбор, коммит появлялся бы всегда, и история стала бы шумом.

## Поиск: инструменты, а не векторная база

Конфиг MikroTik структурирован по путям (`/ip/firewall/filter`) и отлично грепается.
Эмбеддинги здесь только теряют точность: «покажи настройки VLAN 20» — это grep, а не
косинусная близость.

Вместо RAG — карта парка (~10 строк на устройство, генерится детерминированно) в
системном промпте плюс набор инструментов, которыми модель сама добирает детали.
Масштабируется на десятки устройств без отдельной инфраструктуры.

## Права на роутере: группа `ssh,read`

Онбординг создаёт группу `mikrotik-agent-ro` строго с `ssh,read`:

- без `write` — читающий контур физически не может изменить конфигурацию;
- без `sensitive` — роутер **сам** откажется отдавать пароли и ключи, ещё до скраббера;
- без `test` — нет `bandwidth-test` и `flood-ping`, то есть нельзя забить канал.

Проверено: попытка записи под этим пользователем даёт `not enough permissions (9)`.

Цена решения: `/log print` на RouterOS 7.22 требует `test` и потому недоступен.
Остальные 25 представлений живого состояния работают на `ssh,read`. Выдавать `test`
только ради лога — осознанный выбор оператора, по умолчанию не выдаётся.

## Способ входа не равен правам

Ключ или пароль — это лишь доказательство личности; что позволено, определяет группа.
Пользователь с ключом в группе `full` может всё, пользователь с паролем в `ssh,read` —
ничего, кроме чтения. Поэтому защита строится на группе, а не на способе аутентификации.

## Поверхность возможностей модели

Модель ограничена реестром инструментов (`tools.REGISTRY`) и не умеет обращаться к
HTTP-роутам приложения. Единственный инструмент, который вообще касается роутера, —
`get_live_state`, и команда там берётся из таблицы констант: ничего из вывода модели
в неё не подставляется, фильтрация идёт на стороне Python. Поверхности для инъекции
команд нет.

Привилегированная сессия существует только в момент онбординга, инициируется человеком
через форму, пароль админа не попадает ни в базу, ни в лог, ни в аудит.

Тексты конфигураций — особенно комментарии к правилам — это недоверенный ввод, который
пишут администраторы роутеров. Системный промпт это оговаривает; будущий путь записи
обязан опираться на детерминированную валидацию и подтверждение человеком, а не на
суждение модели.

## OpenAI: Responses API, не Chat Completions

`/v1/chat/completions` отвергает function tools вместе с рассуждениями, а актуальные
модели рассуждают по умолчанию — то есть основной режим агента там не работает вовсе.
Адаптер Chat Completions оставлен для совместимых прокси и принудительно шлёт
`reasoning_effort="none"`, когда переданы инструменты.

`store: false` держит конфигурации вне хранилища провайдера; расплата — состояние
рассуждений приходится возвращать самим через `include: reasoning.encrypted_content`.

## Учёт расходов: строка на вызов API, не на вопрос

Один вопрос в чате — несколько вызовов из-за цикла инструментов, и тариф long-context
решается для каждого вызова отдельно. Разделение на uncached/cached/cache-write
обязательно: кэшированный вход в 10 раз дешевле.

Цены лежат в БД (сидятся из каталога в коде), чтобы правиться из UI без пересборки.

## Запись: очередь изменений (фаза 4)

Модель может **предложить** изменение, но не применить его. Инструмент `propose_change`
кладёт план в очередь и всё; применение — действие человека в UI.

**Валидатор детерминированный.** План проверяет обычный Python, а не модель: чёрный
список деструктивных операций (сброс, перезагрузка, прошивка, пользователи, скрипты,
планировщик, файлы, `/import`, скриптовые выражения, склейка команд через `;`), белый
список меню и лимит на количество команд. План с запрещённой командой **отклоняется
целиком** и в очередь не попадает — не правится молча, чтобы «стало можно».

**Отдельный пользователь для записи.** Учётная запись сбора остаётся `ssh,read`.
Запись идёт под `agent-rw` в группе `ssh,read,write` — тоже без `policy` и `sensitive`.
Включается отдельно и по каждому устройству.

**Автоматическое применение отключено (решение от 2026-09-12).** Страховку в виде
автоотката не удалось построить при минимальных правах, а без неё применять изменения
на боевых роутерах нельзя. Установлено на живом железе RouterOS 7.22:

- запись `/system scheduler` **несёт на себе набор политик своего создателя**, и чтобы её
  редактировать, пользователь должен обладать всеми ими. Минимальный пользователь не может
  даже переключить `disabled` — ни с правом `policy`, ни без него;
- `/system backup save` отклоняется при `ssh,read,write`, при `+ftp` и при `+policy`;
  работает только при почти полном наборе прав.

Выдать пользователю записи то, что для этого нужно, — значит отменить само разделение прав,
ради которого он и заведён. Поэтому планы готовятся и проверяются здесь, а выполняет их
человек в Winbox, желательно в safe mode (`Ctrl+X`), который даёт тот же откат при обрыве
связи бесплатно и без лишних прав.

Код применения сохранён и включается настройкой `apply_enabled`. Он станет пригоден, если
подтвердится непроверенная гипотеза: планировщик, созданный с явно **узким** `policy=`,
редактируется пользователем, обладающим тем же узким набором.

**Замысел отката (пока не задействован): откат принадлежит роутеру, а не приложению.** Опасен не плохой командой — её ловит
валидатор, — а хорошей, которая отрезает управление. Поэтому: бэкап под фиксированным
именем → включение заранее установленной задачи отката на N минут → выполнение команд →
человек подтверждает, что устройство живо, и задача выключается. Если связь потеряна,
делать не нужно ничего: роутер восстановится сам.

Задача отката **создаётся один раз при онбординге записи, под админом**: планировщик с
командой в `on-event` требует права `policy`, а оно же даёт управление пользователями.
Дальше агент только переключает `disabled` и `interval`, а сам скрипт изменить не может.
Поэтому же `/system scheduler`, `/system backup load` и `/file` — в чёрном списке
валидатора: план не должен уметь обезвредить собственную страховку.

## Фазы

1. Сбор конфигов, git-хранилище, веб-интерфейс — **готово**
2. Чат с tool-calling, учёт расходов, бюджет — **готово**
3. Живое состояние в пределах `read` — **готово**
4. Запись через очередь с подтверждением — **готово в коде**, на реальном железе путь
   записи ещё не провизионился
